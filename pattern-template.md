# Pattern Template

Use this template when a repeated workflow choice has shown up often enough to deserve its own pattern.

## Pattern name

Use a short name that describes the operating behavior, not a specific tool.

## Problem

What recurring failure, ambiguity, or bottleneck does the pattern address?

## When to use it

List the conditions that make the pattern useful.

## Workflow

Show the smallest useful sequence of stages. Prefer a simple diagram when the handoff or decision logic matters.

## Human role

State what the person still owns. Be explicit about judgment, approval, escalation, or interpretation.

## Failure mode

Describe how the pattern can be implemented badly or overused.

## Example

Use a public-safe example that makes the operating logic concrete.

## Evidence in the portfolio

Link to at least two demonstrated examples when possible. If the pattern is primarily demonstrated in one project, say so rather than implying broader evidence.

## Pattern admission rule

A useful pattern should be:

- repeatable across more than one task or context
- explainable without depending on a specific vendor
- specific enough to change how the workflow is designed
- easy to distinguish from a generic principle or slogan
- grounded in demonstrated work rather than invented to make the library larger

If it does not meet those conditions, keep it as a project-specific design choice rather than promoting it into the library.
